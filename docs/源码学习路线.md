# Humbert Agent 源码学习路线

> 根据 2026-10-22 的源码整理。本文安排阅读顺序、入口、目标和练习；具体实现细节配合 [项目源码详解](项目源码详解.md) 与 [RAG 源码详解](RAG源码详解.md) 查阅。

建议围绕真实操作阅读：启动应用、发送消息、读取文件、批准工具、导入文档、检索引用。每次追踪一个操作从入口到持久化、再到界面反馈的完整过程。

## 如何使用这条路线

分三轮推进，每轮都有明确产出：

| 轮次 | 阅读范围 | 完成标志 |
| --- | --- | --- |
| 第一轮：建立主干 | 第 1–4 阶段，再读第 7 阶段的发送/返回链路 | 能画出一条普通聊天的调用链，说明用户消息与回答何时保存 |
| 第二轮：逐项展开 | 第 5–6 阶段，以及第 8–11 阶段 | 能独立追踪一个文件工具、一条审批、一次 RAG 导入/查询和一种扩展能力 |
| 第三轮：检查工程边界 | 每阶段的失败路径及第 12 阶段 | 能解释取消、重试、重启、配置变化、并发和关闭后的状态 |

第一遍遇到不熟悉的辅助函数，先记录它的输入、输出和副作用，沿主流程继续。第二遍再进入具体实现；平台原生代码、迁移 SQL、解析算法适合在业务链路清楚后专项阅读。

### 每个模块统一记录六件事

1. **入口**：哪个 Service、工具、事件或后台任务会调用它？
2. **契约**：输入/输出类型及接口在哪里？调用者依赖它的哪些保证？
3. **事实**：数据由谁拥有，写到哪里，哪些内容可以重建？
4. **状态**：配置何时冻结，活动操作如何登记，锁与事务覆盖什么？
5. **失败**：报错、取消、超时、重试后分别留下什么？
6. **退出**：谁停止生产新工作，谁等待在途操作，谁释放资源？

记录模板：

```text
模块 / 场景：
入口 → 核心调用 → 持久化 → 事件 / UI：
主要类型与 ID：
资源和数据所有者：
锁 / 事务 / 版本检查：
成功 / 失败 / 取消 / 重试：
尚未弄清的问题：
```

## 阅读前先建立六个概念

| 概念 | 在项目中的意义 | 先看哪里 |
| --- | --- | --- |
| Agent | 用户长期保存的模型、指令、能力和工作区配置 | [agents/types.go](../internal/agents/types.go) |
| Session | 属于某个 Agent 的持续对话；包含控制面信息与消息历史 | [sessions/types.go](../internal/sessions/types.go) |
| Turn / Snapshot | 一次用户请求及模型—工具循环；本轮捕获模型、工具和安全等配置 | [runtime/types.go](../internal/runtime/types.go) |
| Transcript | JSONL 消息树与压缩记录，是历史消息事实来源 | [transcript/types.go](../internal/transcript/types.go) |
| Context | 从历史和配置构造的有限模型输入窗口 | [contextengine/types.go](../internal/contextengine/types.go) |
| Capability / Scope | 本轮开放的工具能力，以及由宿主确定的身份、安全和工作区范围 | [tools/types.go](../internal/tools/types.go)、[module_contracts.go](../internal/runtime/module_contracts.go) |

同时记住 AgentID、SessionID、RequestID、RunID、EntryID、ToolCallID 的区别。调试时把同一个场景中的这些 ID 串起来，比只按时间搜索日志更可靠。

## 1. 启动与装配：先看应用如何组成

**入口与顺序：**

1. [cmd/desktop/main.go](../cmd/desktop/main.go#L36)：`run`、`runDesktop`。
2. [app/application.go](../internal/app/application.go#L125)：`Bootstrap`，先只看构造顺序、依赖参数和错误返回。
3. [app/runtime.go](../internal/app/runtime.go)、[tasks.go](../internal/app/tasks.go)、[modules.go](../internal/app/modules.go)：展开三段装配。
4. [services/enter.go](../internal/services/enter.go)、[dependencies.go](../internal/services/dependencies.go)：观察 Core 如何变成 Wails 服务。
5. [app/lifecycle.go](../internal/app/lifecycle.go)：回头看启动失败和正常关闭。

```text
取得数据目录锁 → 启动前恢复/备份 → Bootstrap
  → 基础服务 → Runtime → Tasks → 默认 Knowledge / 追加模块
  → 注册 Wails 服务 → 运行窗口
退出 → 停止后台工作 → 等待 Runtime → 关闭连接和存储
```

**需要弄清：** Application 负责装配；领域服务拥有业务；Usecases 协调跨领域操作。默认 Knowledge 会加载本地状态，数据库按需连接。创建对象不一定表示已连接外部服务或启动后台 Worker。

**练习：** 画一张“谁构造谁、谁关闭谁”的图，选一个中途构造失败的位置，沿清理清单确认哪些资源已经归宿主管理。

参考：[App README](../internal/app/README.md)、[源码详解第 2 章](项目源码详解.md#bootstrap)。

## 2. 领域对象与持久化：弄清数据保存在哪里

按“类型 → 业务方法 → Store → 编码/恢复”阅读：

| 模块 | 建议顺序 | 重点问题 |
| --- | --- | --- |
| Agent | [types.go](../internal/agents/types.go) → [service.go](../internal/agents/service.go) → [store.go](../internal/agents/store.go) | 配置保存、工作区归属、能力选择如何校验？ |
| 模型配置 | [models/types.go](../internal/models/types.go) → [store.go](../internal/models/store.go) | Provider、Model、凭据引用和实际模型实例有什么关系？ |
| 会话业务 | [sessions/types.go](../internal/sessions/types.go) → [service.go](../internal/sessions/service.go) → [store.go](../internal/sessions/store.go)、[catalog.go](../internal/sessions/catalog.go) | 创建、改名、归档、分页分别读写什么？ |
| 消息历史 | [transcript/types.go](../internal/transcript/types.go) → [store.go](../internal/transcript/store.go) → [codec.go](../internal/transcript/codec.go) | Entry、父节点、消息与压缩记录如何表达？ |

先抓住三个存储边界：

- Agent 配置位于各 Agent 目录中的 config.json。
- 会话标题、归属、归档等控制面信息位于 `session-metadata.sqlite`。
- 消息、thinking、ToolCall、ToolResult 和压缩记录位于 Session JSONL。

之后再读 Transcript 的 `cache.go`、`location_index.go`、`history_index.go` 和 `journal.go`，理解长历史按需读取、索引失效和崩溃恢复。Session 附件与完整工具结果归档分别看 `attachments.go`、`artifacts.go`。

**练习：** 跟踪 `Session.Create` 和 `PrepareUserMessage`；解释“归档会话”“压缩历史”“删除会话”各自修改哪些数据。检查数据时使用实验数据或副本，避免手工编辑正在运行的 JSONL/SQLite。

参考：[持久化详解](项目源码详解.md#persistence)。

<a id="phase-03"></a>
## 3. 一轮普通聊天：项目最重要的主线

先选择一条纯文本、无需工具和图片的消息。此时可以暂时跳过 RAG、MCP、Skill、视觉和审批分支。

```text
前端 Runtime Store.send → api/chat.startTurn
  → ChatService.StartTurn
  → runtime.Service.StartTurn
  → sessions.PrepareUserMessage
  → Resolver.ResolveTurn
  → executeTurn → Executor.Execute → Eino Runner
  → consumeEvents → 保存完整 Assistant / Tool 步骤
  → handleExecutionOutcome → 收尾与终态事件
  → 前端重新同步 Session 历史
```

**重点入口：**

| 阅读位置 | 这遍要看什么 |
| --- | --- |
| [services/chatservice.go](../internal/services/chatservice.go) | 桌面请求如何转成 StartTurnInput，返回收据包含什么 |
| [runtime/service.go](../internal/runtime/service.go#L131) | `StartTurn` 的 reservation、用户消息落盘、快照与异步启动顺序 |
| [runtime/resolver.go](../internal/runtime/resolver.go#L105) | `ResolveTurn` 如何得到本轮 Snapshot；第一遍把 Context/能力装配当作子流程 |
| [runtime/eino_builder.go](../internal/runtime/eino_builder.go#L23) | `buildChatModelAgent` 如何将模型、工具、Handlers 和限制交给 Eino |
| [runtime/executor.go](../internal/runtime/executor.go) | `Execute`、`buildRunner`、`consumeEvents` 如何接收 Eino 事件并保存完整结果 |
| [runtime/runs.go](../internal/runtime/runs.go)、[events.go](../internal/runtime/events.go) | 成功、失败、取消、审批中断如何分流，何时释放会话占用 |

**需要弄清：** 用户消息先保存，Resolver 再读取历史；StartTurn 返回的是启动收据；Eino 拥有模型—工具循环，Humbert 在外围负责持久化、能力、安全、预算和生命周期。流式字符用于实时界面，完整步骤进入历史。

**练习：** 以同一个 RequestID 跟踪一次消息，标出“用户已落盘”“Snapshot 完成”“第一次模型输出”“Assistant 已保存”“Turn 终态”五个时刻。再读初始化失败后的 RetryUserMessageID，解释为什么重试可以避免重复追加用户消息。

参考：[Runtime README](../internal/runtime/README.md)、[一轮执行详解](项目源码详解.md#runtime)。

| 压缩和附件 | [contextengine/compactor.go](../internal/contextengine/compactor.go)、[middleware.go](../internal/contextengine/middleware.go) → [sessions/attachments.go](../internal/sessions/attachments.go) → [multimodal/replay.go](../internal/multimodal/replay.go)、[vision_bridge.go](../internal/multimodal/vision_bridge.go) |

**先回答：** 哪个模型负责聊天、摘要和图片观察？工具 Schema 占多少预算？历史如何从有效检查点和尾部消息构造？哪些附件需要重新读取？thinking 回放策略由什么决定？

随后读软/硬预算、运行中 pending summary、成功后的 Commit，以及 `ExpectedLeaf` 的分支检查。压缩是追加检查点，原始消息仍保留；在途摘要和持久化摘要有不同提交时机。

**练习：** 对照一条保存消息和对应的 Provider 消息，标出时间戳、附件、thinking、摘要和工具结果预览的来源。用单独的实验会话观察一次手动压缩，确认原始消息仍可回查。

参考：[Context 详解](项目源码详解.md#context)、[附件详解](项目源码详解.md#multimodal)。

<a id="phase-06"></a>
## 6. 权限、审批与沙箱：完整读一次暂停和恢复

顺序为 [tools/guarded_tool.go](../internal/tools/guarded_tool.go) → [permission/engine.go](../internal/permission/engine.go) → [approval/manager.go](../internal/approval/manager.go) / [checkpoint_store.go](../internal/approval/checkpoint_store.go) → [runtime/approvals.go](../internal/runtime/approvals.go) → `Executor.Resume`。

```text
调用工具 → Evaluate
  Allow → 执行原工具
  Deny  → 返回拒绝
  Ask   → Eino interrupt → 保存待审批运行 → 用户决定
        → ResolveApproval → Resume 原 checkpoint → 执行或拒绝
```

然后阅读 [sandbox/manager.go](../internal/sandbox/manager.go)、[pathguard.go](../internal/sandbox/pathguard.go)、[access.go](../internal/sandbox/access.go)，再按当前操作系统进入一个 `platform_*.go`。

**需要弄清：** 工具是否允许调用、文件路径是否允许访问、进程如何被操作系统隔离，是三个检查点。权限模式与 Sandbox 配置会影响实际策略，应沿冻结的 EffectivePolicy 判断边界。

等待审批时，执行 Worker 可以结束，但 Session reservation 和 checkpoint 仍被保留。批准后使用原调用参数恢复；拒绝、超时和用户取消的收尾路径需要分别读。当前 checkpoint 属于进程内运行状态，重启恢复要按现有中断语义理解。

**练习：** 对一个临时文件写操作分别做批准、拒绝和取消；在 `registerInterruptedRun`、`resolveApproval`、`resumeTurn` 附近观察运行阶段及占用何时释放。

参考：[Permission](项目源码详解.md#permission)、[Approval](项目源码详解.md#approval)、[Sandbox](项目源码详解.md#sandbox)。

## 8. RAG 装配与导入：先业务流程，再进入算法

先从桌面知识库理解真实调用，再用独立示例缩小范围：

| 阅读顺序 | 入口与目标 |
| --- | --- |

| 2. 业务状态 | [knowledge/settings.go](../internal/knowledge/settings.go)、[manager.go](../internal/knowledge/manager.go)：Values、凭据、知识库/Agent 绑定 |
| 3. 冻结与装配 | [lifecycle.go](../internal/knowledge/lifecycle.go#L19) 的 acquire → [engine.go](../internal/knowledge/engine.go#L32) 的 buildEngine：锁外连接、配置 revision、资源占用和关闭 |
| 4. 导入队列 | [jobs.go](../internal/knowledge/jobs.go)：先保存原件，再排队、取消、重试和重新索引 |
| 5. 精简入口 | [example.go](../examples/5-rag/example.go) → [upload/main.go](../examples/5-rag/upload/main.go)：观察完整依赖装配 |
| 6. 底座契约 | [rag/rag.go](../internal/rag/rag.go)、[service.go](../internal/rag/service.go)、[persistence.go](../internal/rag/persistence.go)：依赖、请求、状态与版本接口 |

示例使用 example.go 的固定配置；upload 会初始化数据库并写入文档。运行前配置专用实验数据库、文件与模型，按 [示例 README](../examples/5-rag/README.md) 核对参数来源。

导入主线按以下顺序深入：

```text
knowledge.Upload → 保存原件 → queue / launch / runImport
  → rag.Ingest → 预留 attempt / 处理状态
  → Loader / documenttext → Markdown、图片与来源
```

**需要弄清：** 两路原始分数与 RRF 排名、精排分数如何区分？父块扩展如何保留真实命中子块？无效/未发布记录在哪里过滤？超过上下文预算时怎样选块？引用失效后历史快照如何展示？

**练习：** 对同一问题比较 semantic、keyword、hybrid 的命中、原始通道分数和最终上下文；再改变绑定或文档版本，观察旧来源链接的校验。质量评测先读 references 标注与分母计算，再解释 P@K/R@K/RR/nDCG。

参考：[Search](RAG源码详解.md#search)、[Hybrid](RAG源码详解.md#hybrid)、[引用](RAG源码详解.md#context)、[评测](RAG源码详解.md#evaluation)。

## 阅读时持续核对的事项

- **配置与快照**：修改全局配置影响哪次调用？已有 Turn/导入使用的对象是否已冻结？
- **接口与具体实现**：先看调用者实际依赖的方法，再进入当前装配的实现。Eino 的循环、Humbert 的业务编排和各 SDK 的网络行为分层追踪。
- **锁与事务**：锁保护什么，网络/模型调用是否在锁外，提交前用什么版本条件复核？锁和事务不能自动提供跨数据库原子性。
- **取消与关闭**：调用返回可能只是停止等待；后台清理、版本回写和池关闭分别何时结束？注意 WaitGroup 登记、release/Close 所有权及独立清理 Context。
- **副作用与重试**：错误发生时是否可能已经提交？先查业务 ID、attempt、已发布状态或消息收据，再解释能否安全重试。
- **原文与投影**：JSONL、原件、权威分块、模型 Context、实时 UI、搜索缓存各承载什么？不要用展示预览推断唯一原文。
- **坐标与单位**：字节、rune、近似 Token、图片预览坐标、PDF 页码分别计算；特别检查范围是否包含标题拼接与图片识别文字。
- **示例与正式入口**：先看示例配置与装配，再回到桌面链路补齐 Guard、状态、生命周期和失败处理。

验证方式见 [持续验证说明](持续验证说明.md)。阅读本身可以先保持源码不变；需要实验时使用临时工作区、单独会话和实验知识库，记录实际运行条件。

## 第一轮结束的自测

能够不翻源码回答下面的问题，就可以开始按模块深入：

1. 从点击发送到模型第一次收到输入，中间经过哪些对象？
2. 用户消息已经保存但初始化失败，后端和前端如何支持重试？
3. Eino 承担哪些工作，Humbert 在哪些入口接管业务和安全？
4. 工具名称、Schema、实际实例与授权身份如何保持一致？
5. 为什么同一 Session 等待审批时不能再启动普通 Turn？
6. 压缩后原始历史在哪里，模型实际看到哪些消息？
7. RAG 的原件、处理状态、已发布版本、分块和历史引用分别由谁拥有？
8. 新增一个业务能力，需要接入哪些模块，哪些现有流程可以复用？
