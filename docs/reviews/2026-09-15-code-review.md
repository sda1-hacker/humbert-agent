## 一、结论

项目不需要推倒重写。Go 核心与 Wails 适配层分离、每轮运行快照、权限审批与沙盒分层、JSONL 会话记录等基础值得保留。

当前主要失衡是：工具与配置管理做得很深，但会话异常恢复、运行生命周期和个人助理的日常交互尚未闭环。新增功能之前，应先修复会话可靠性问题，再清理未接入代码和缩减维护面。

### 代码量

统计排除了生成的 bindings、依赖和构建产物；统计的是物理行，包含注释和空行，不代表复杂度或测试覆盖率。

## 二、当时识别的逻辑问题

P1 表示应在继续扩展能力前修复；P2 表示需要安排处理的正确性或扩展性问题。

### F1 · P1：取消或异常后，未闭合的工具调用可以进入下一轮上下文

证据：`internal/contextengine/projection.go:151`，`internal/runtime/executor.go` 的 Assistant/Tool 持久化逻辑，以及 runtime 的取消收尾。

当前校验仅确认 ToolResult 能找到先前的 ToolCall，没有确认每个 ToolCall 都收到结果，也没有阻止未完成调用后出现新的 UserMessage。执行器先持久化 Assistant ToolCall，再执行工具；等待审批时取消、工具异常或结果落盘前取消，都可能留下不完整历史。Tool 结果持久化使用可取消的 context，已发生副作用与已记录结果还可能分离。

临时测试构造 `User → Assistant(tool call) → User`，调用现有校验函数，实际返回成功，已复现校验缺口。没有进行真实 Provider 请求；此类历史可能被严格校验工具协议的 Provider 拒绝。

建议：

- 用待完成调用集合校验完整事务，覆盖重复结果、未回答调用和消息边界。
- 取消、异常和进程重启时统一处理未闭合调用，记录明确的 cancelled/unknown 状态并生成协议合法的上下文。
- 已执行但结果未知时，不得自动重放有副作用的工具；不能把“未记录结果”解释为“没有执行”。
- 给结果记录一个有界、不随用户取消立即丢失的收尾窗口。

验收：审批中取消、工具执行中取消、执行后落盘前中断，重启后均可继续会话，且不会重复执行写入。

### F2 · P1：一个半创建的会话会阻止整个会话存储初始化

证据：`internal/sessions/store.go:173` 先创建 transcript，再在第 209 行写 config；`rebuildIndex` 第 458–463 行遇到缺失或无效 config 直接失败，错误向上传递到应用初始化。

普通错误有回滚，但进程在两次写入之间退出时回滚不会执行。临时测试只创建 transcript 后调用 NewStore，已复现整个 Store 初始化失败。

建议：先在暂存目录创建完整会话，再原子发布；启动时识别暂存目录和不一致会话，对损坏会话提供隔离/修复入口，使其他会话仍能使用。不能静默删除用户历史。单个文件的原子写不等于多个文件的事务。

### F3 · P2：回答完成后的维护仍占据运行状态，而且取消不能停止它

证据：`internal/runtime/service.go:708`。completeTurn 同步执行 MaintainAfterTurn，结束后才发送完成事件并释放会话；维护 context 来自 rootCtx，而 CancelTurn 取消的是 active context。

影响：用户已经看到完整回答，界面仍忙碌；点击停止不能取消本次维护，最终仍可能收到 completed。维护包含模型调用时尤其明显。

建议：明确区分回答完成与上下文/记忆维护。短期保留同步流程时暴露 maintaining 状态并统一取消；之后再考虑受管理、按会话串行并带游标校验的维护队列，避免后台任务覆盖新一轮状态。

### F4 · P2：发送失败可能已经保存了用户消息，重试会重复提交

证据：`internal/runtime/service.go:156` 先保存用户消息，再 ResolveTurn；失败返回空 StartTurnResult。`frontend/src/stores/runtime.js` 的启动失败分支不刷新已经持久化的消息。

影响：凭据或运行快照解析失败时，前端显示发送失败，但历史里已有该消息；直接重试又追加一条。初始化中的耗时操作也还没有交给前端可取消的运行句柄。

建议：引入 clientMessageID/requestID 幂等语义、已接受与执行失败的明确状态；返回持久化消息标识并同步界面。基础依赖可预校验，但不要简单交换 append 与 ResolveTurn，因为上下文解析需要当前用户消息。

### F5 · P2：启动 Worker 与 Close 存在生命周期竞态

证据：`internal/runtime/service.go:189–199` 注册 active 后解锁，再 wg.Add；Close 在第 1058 行附近设置 closed 并解锁，然后等待 WaitGroup。审批恢复路径也应一起审查。

静态可构造的交错：Close 在 Add 之前观察到计数为零并返回，随后才启动 Worker，依赖可能已关闭。尚未用调度控制测试复现。

建议：在同一个生命周期锁内完成接收检查和 Worker 计数注册；初始化、恢复和维护也必须纳入关闭边界。用阻塞式 fake resolver/executor 构造并发回归测试。

### F6 · P2：会话删除只在前端检查运行状态

证据：`internal/services/sessionservice.go` 的 DeleteSession 直接删除存储；前端 sidebar 在打开删除确认框前检查运行状态。

前端检查存在过期窗口，不能保证后端删除时会话没有运行。删除后工具可能继续执行，随后历史写入失败。此项是静态控制流判断，未做完整 UI 复现。

建议：由应用服务统一执行删除，使用与启动同一套会话占用机制；默认返回 SessionBusy，或明确执行取消、等待结束、再删除。

### F7 · P2：JSONL 每次追加都全量扫描，长期会话扩展性不足（已修复主要路径）

原始问题是 `appendEntry` 每次都调用 `loadLocked`，持续追加的累计解析工作量可能趋近
O(N²)。现在完整尾行只做 O(1) 检查；首次加载严格校验 JSONL 后进入容量受限的可重建
Document LRU，正常追加直接验证缓存文件身份并增量推进 Leaf/Active Branch。尾部修复、
文件大小/修改时间/身份变化或 LRU 淘汰都会使缓存失效并从 JSONL 重建。

LoadSession 返回深拷贝，调用方不能污染缓存。Compaction Prepare 复用同一次 Document
读取。缓存还维护 Message ID/序号到 Active Branch 位置的索引，分页只复制当前窗口，
不再克隆或筛选完整 Document；JSONL 仍是唯一权威消息存储。

后续只需基于真实长会话继续观察 LRU 容量和首次冷加载成本；不需要因此改用 SQLite，也
不要另造第二份权威消息存储。

### B. 缩减维护面，比减少行数更重要

| 区域 | 建议 | 保留边界 |
| --- | --- | --- |
| Web 搜索 | websearch_tool/backends 合计约 2,966 行；选常用 API 加一个备用源，其余按实际需求裁剪 | 超时、响应大小限制、网络地址校验 |
| Skills 管理 | 先保留本地/ZIP/一个常用远程来源；多平台来源、别名、更新策略按使用频率收缩 | 路径验证、完整性校验、脚本执行约束 |
| Wails services | 合并重复 DTO 映射和统一错误边界，保持薄适配层 | 不把业务迁回 UI 或塞进通用“大框架” |
| 前端 runtime store | 以 runId/requestId 为中心定义状态转换，拆出事件归并与 ToolTrace 投影 | 流式增量、落盘历史与当前状态的明确关系 |
| 大型设置页 | 按 Provider 表单、来源表单、列表、弹窗等职责拆组件 | 安装包与 Agent 引用的语义区别 |
| HTTP 安全帮助逻辑 | 比较 web_fetch 与技能下载策略，适合时抽出小型公共模块 | 重定向与实际拨号地址校验；不能换成裸 http.Get |
| 配置加载 | 统一公共装载与默认值处理 | 凭据单独存储，不能为“精简”并回普通配置 |
| 排版与模板资源 | 统一换行风格，清理确认无引用的模板资源 | 不用删注释、压成一行美化指标 |

这些是产品范围取舍，不意味着所有已工作的可选能力都应删除。优先删死代码，再依据自己每天使用的功能裁剪。

### C. 应保留的设计

- permission 决定是否允许，approval 管理暂停与用户决策，sandbox 限制实际执行环境；三者不能因看起来重复而合并。
- 工具统一包装、取消传播、输出限额、路径隔离和凭据隔离。
- 每轮冻结模型/工具/配置快照，避免运行中设置变更造成不一致。
- Session 与 Transcript 分工、JSONL 事实记录、每会话并发控制。
- contextengine 与 memory 的职责边界；调整调度和记忆作用域，不必全部重写。

## 六、当时建议的实施顺序

### 第一阶段：可靠运行

修测试编译和临时路径基线 → F1/F2 → 发送幂等与维护取消 → 生命周期及删除并发。

验收：用户能随时停止、失败后重试、退出后重开；不会因为单个异常会话打不开应用，不会无意重放工具副作用。

### 第二阶段：收缩与整理

删除 4 个未接入文件；统一真实架构文档；分批整理前端 run 状态、DTO 和设置页；按个人使用习惯裁剪搜索和技能来源。

每批只改变一个边界，保持可独立回退。不要同时重写存储、runtime 和前端状态。

### 第三阶段：可每天使用的个人助理

Markdown/代码块 → 历史分页与失败消息操作 → 文件附件/图片 → 产物与工作区预览 → 跨会话个人记忆及编辑/遗忘。

记忆建议明确分 user、agent、session 作用域，记录来源和更新时间。事实与偏好允许修订；删除原会话时如何处理派生记忆需要明确规则。不要把所有聊天自动永久注入每轮请求。

### 第四阶段：任务与自动化

先设计 Task 状态、触发来源、最大时长/步数/费用、取消和结果记录，再接一次性后台任务、定时触发和 Goal 循环。应用未运行时是否执行，是桌面内调度与独立守护进程的选择，需按实际需求决定。

随后才评估浏览器自动化、多 Agent 协作、跨端入口。它们都不是当前“个人助理能稳定使用”的前置条件。

## 七、技术路线

继续采用 Vue → Wails services → 应用/runtime → Eino 与工具适配层 → 文件存储/系统能力。Eino 负责模型与 Agent 执行组合；humbert 自己负责持久化、运行状态、权限、恢复和桌面体验，不能期待更换框架版本自动解决这些问题。

当前 go.mod 为 Eino v0.9.19、Wails v3.0.0-beta.6；前端 Wails runtime 使用 latest 声明。建议锁定并验证前后端兼容的版本组合后再升级。本报告基于本地版本审查，没有核验它们是否为网络上的最新发布版本。

最值得先做的下一次提交：修复 F1/F2 并补回归测试。最不值得先做的事情：继续堆搜索后端、技能市场来源或重新设计一套插件框架。
